Hydra — Architecture

Nine agents.
One human gate.

Hydra carries a job search from raw listing to a reviewed, ready-to-submit application. Each step is a separate agent with a narrow job and its own failure mode. Nothing is ever submitted without a person approving it first — that gate is enforced in code, not by convention.

Human-in-the-loop React · Vite · Supabase OpenRouter → Groq → Anthropic Public repo

The problem

Autonomy is the easy half. Restraint is the hard half.

A pipeline that can find jobs, write tailored applications and submit them is not difficult to build. A pipeline you would actually let near your professional reputation is a different thing entirely.

Hydra is built around that second problem. Every agent is narrow enough to be inspectable, every listing is checked against a live source before it can reach you, and the submission step is physically unreachable until a human presses approve.

The pipeline

What each agent does

In order. Each is a separate module under src/agents/.

01
Scout scout.ts

Finds openings by scanning applicant-tracking-system boards directly — Greenhouse, Ashby, Lever, SmartRecruiters, Recruitee — rather than scraping aggregators.

Unions the built-in company list with boards the user has added, de-duplicated by slug. A company is only ever added after its board is probed and confirmed to exist, so the registry cannot fill with guessed slugs.

02
Classifier classifier.ts

Scores each listing for fit and assigns it to a CV track. Runs singly or batched.

Injects the user's own preferences — preferred titles, anti-signals, seniority, target companies — into the prompt, but only when a custom profile exists. Default scoring stays untouched otherwise.

03
CV Selector cvSelector.ts

Picks which of three maintained CV tracks to build from — ux, pm or devrel. Not one CV bent to fit; three genuinely different positionings.

04
Resume Tailor resumeTailor.ts

Adapts the selected CV to the specific listing — emphasis and ordering, working from real history rather than inventing it.

05
Cover Letter Writer coverLetterWriter.ts

Drafts a letter against the job description and the tailored CV, so the two documents agree with each other.

06
Form Mapper formMapper.ts

Detects which ATS platform a posting lives on from its URL, and maps the generated material onto the fields that platform expects.

Platform detection is deterministic, from the URL — not a model call. There is no reason to spend a model on something a regular expression answers correctly.

07
Screenshot Capturer screenshotCapturer.ts

Renders the filled application through a headless browser worker, so the reviewer sees the actual form as the employer will receive it — not a JSON summary of it.

Requires a deployed Cloudflare Browser Worker. Without one this stage degrades and reports itself unavailable; it does not fail the run or silently skip review.

08
Review Gatekeeper reviewGatekeeper.ts Human required

Everything above this line produces a proposal. Nothing below it runs until a person approves.

Enqueues at pending_review, then waits for an explicit approve() or reject(). Jobs already in a terminal state — rejected, submitted, archived — cannot be re-enqueued, so a re-run can never quietly resurrect something you already turned down.

09
Status Tracker statusTracker.ts

Watches for employer replies after submission and moves each application's status accordingly, so the board reflects reality without manual upkeep.

Supporting modules — not pipeline stages

submitter.ts performs the actual submission and fires only after the Gatekeeper approves. openRouterClient.ts is the shared model client. types.ts holds the contracts between agents.

The gate

Why the interesting part is where it stops

The Review Gatekeeper is the design decision the rest of the system exists to serve. An agent pipeline that submits on your behalf is a liability the first time a model misreads a listing. One that prepares complete work and then waits is an assistant.

Three properties make it hold:

  • Submission is unreachable without approval — submitter.ts runs downstream of the gate, not in parallel with it.
  • Decisions are terminal — once rejected, submitted or archived, a job cannot be re-queued by a later run.
  • Review sees the real artefact — the screenshot stage renders the actual filled form, so approval is based on what the employer receives.
Verification, before review

Listings are checked against a live ATS source before they can reach the queue. Anything unverified is badged UNVERIFIED and is never eligible for automatic handling — the failure mode of a hallucinated job posting is a wasted application, so it is caught upstream.

CV tracks

Three positionings, not one résumé

The Classifier assigns a track; the CV Selector loads it. They are maintained separately because they make genuinely different arguments.

Failure behaviour

What happens when something breaks

Degradation is designed rather than accidental. The pipeline is worth more when it is honest about being partially available than when it pretends otherwise.

FailureBehaviour
Model provider unavailableFalls through OpenRouter → Groq → Anthropic, whichever key is present. Free models are discovered live rather than hardcoded, because :free model IDs are retired constantly.
Model returns malformed JSONParsed and validated inside the retry loop, so a truncated response advances to the next model instead of failing the request.
Browser worker not deployedScreenshot stage reports unavailable. Review still happens, without the visual.
Listing cannot be verifiedBadged UNVERIFIED, excluded from automatic handling.
Reviewer rejectsTerminal. The job cannot re-enter the queue on a later run.
